# 代码或文档改动前置逻辑

- 改动前先理解用户的目标、改动对象、范围、约束和预期结果；结合用户描述、现有文件及上下文核实，不凭模糊表述自行扩大范围。
- 判断是否已达到足以准确执行的理解程度：能够说明要改什么、为什么改，以及如何判断结果符合要求；涉及关键边界或行为变化时，也应明确其预期。
- 涉及 API 的改动，先结合相邻说明和示例识别重点 API，确认其作用、适用场景以及与本次改动有关的调用方式、参数、输入输出和限制；优先查阅官方资料核实版本和行为。无法核实的信息标为待确认，不凭记忆断言。
- 若关键需求仍有歧义，先提出具体问题，尽量一次集中询问；可提供选项或说明各选择的影响。用户回答后重新判断，仍有关键疑问时继续澄清，直到理解充分再改动。
- 已明确的信息不重复询问；不影响目标和结果的细节可根据上下文作合理判断。澄清期间可读取相关资料，但不修改代码或文档。
- 用户明确指定的范围和要求优先；执行中发现新的关键歧义或需要超出原定范围时，先与用户确认。

# 技术文档编写规范

- 面向初学者讲解，表达简洁；首次出现的关键概念要解释清楚。
- 优先使用有序列表、无序列表和表格组织内容；流程或关系较复杂时，再使用流程图辅助理解。
- 正文以概念和原理为主，不绑定到某个实际 Demo 的文件路径或具体实现；有助于理解的示例可按需加入，并与相关 Demo 保持一致。
- 提供代码示例时，在关键学习点添加简短中文注释；注释说明学习要点，不逐行复述显而易见的代码。
- 介绍或修改涉及重点 API 的内容时，即使用户只指定了局部行，也要结合相邻说明和示例检查讲解是否完整，并在用户指定范围内补齐必要信息；确需超出范围时先确认。先介绍重点 API 和示例中的关键 API，再给出示例；介绍时必须解释其作用和适用场景，并根据读者理解和示例需要说明调用方式、关键参数、输入输出、返回值及使用限制；不罗列无关参数，不重复已有的充分且准确的说明。涉及 API、版本、兼容性或安全等易变化内容时，优先查阅官方资料，注明来源及核实的适用版本；无法访问资料或确认版本时，明确标注待核实，不凭记忆断言。完成前核对上述要求及 API 说明与示例的一致性；不能完成核实时，向用户说明具体限制。
- 保证内容完整闭环、前后术语一致；合并重复说明，避免同一知识点在多处反复解释。
- 完成前检查示例与说明是否一致、代码注释是否清楚，以及是否存在遗漏或重复。

## 学习小结

- 不使用固定章节模板或标题白名单。
- 根据主题、可用资料和用户目标拟定章节提纲，先交由用户确认或调整；确认后再撰写正文。
- 用户已给出章节提纲时，直接沿用，不重复要求确认。
- 章节按主题需要组织，可涵盖概念、原理、使用场景、API、示例、边界或排查等；不为填满清单而强行添加章节。
- 从技术文档视角解释职责、流程、输入输出和约束，不逐行翻译现有 Demo 代码，也不依据文件数量或目录结构扩展章节。
- 上下文不足时，不虚构实现细节；无依据的内容省略或明确标为待确认。
