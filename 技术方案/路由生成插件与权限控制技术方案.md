# 路由生成插件与权限控制技术方案

## 一、需求概述

### 背景

项目采用约定式路由（Convention-based Routing）方案，通过 Vite 插件 `vite-plugin-react-auto-router` 自动扫描 `src/pages/` 目录结构并生成 React Router v6 路由配置。同时，项目需要支持基于角色的访问控制（RBAC），包括菜单级、路由级和按钮级权限管理。

---

## 四、路由生成设计

### 当前路由生成规则

| 文件          | 作用                                            | 生成路由类型 |
| ------------- | ----------------------------------------------- | ------------ |
| `index.tsx`   | 当前目录对应的页面组件                          | 独立路由     |
| `_layout.tsx` | 当前目录的嵌套布局组件，内部需渲染 `<Outlet />` | 父级路由     |
| `guard.tsx`   | 路由守卫组件，会包裹当前目录的 `element`        | 守卫路由     |
| 目录名 `404`  | 特殊处理，生成通配路径 `*`，用作 404 兜底页     | 通配路由     |

### 嵌套规则

项目支持**双模式**嵌套路由生成策略，通过 `vite.config.ts` 中的 `nestedByDirectory` 配置切换。

#### 模式一：`_layout.tsx` 作为嵌套开关（默认，向后兼容）

**配置**: `nestedByDirectory: false` (默认值)

- 目录有 `_layout.tsx` → 当前目录变成父路由，子目录挂到 `children`，子页面通过 `<Outlet />` 渲染
- 目录无 `_layout.tsx` → 当前目录是独立路由，子目录被提升为平铺路由
- 一旦进入某个 `_layout.tsx` 的嵌套上下文，其所有后代目录都会继续嵌套，即使后代目录自己没有 `_layout.tsx`

**简记**：看有没有 `_layout.tsx`，不看目录层级。

#### 模式二：UmiJS 风格的目录驱动嵌套（新增）

**配置**: `nestedByDirectory: true`

- 基于目录结构自动生成嵌套路由，无需 `_layout.tsx`
- 有子目录的目录会自动成为父路由容器
- 父路由容器没有 `index.tsx` 时，`element` 为 `null`（React Router v6 原生支持）
- 父路由容器有 `index.tsx` 时，正常生成 `element`

**简记**：看目录层级，有子目录就嵌套。

#### 对比示例

```
目录结构：
a/
├── index.tsx
├── b/
│   └── index.tsx
└── c/
    └── index.tsx

模式一 (nestedByDirectory: false)：
生成：/a         ← 独立路由
     /a/b        ← 平铺路由
     /a/c        ← 平铺路由

模式二 (nestedByDirectory: true)：
生成：/a         ← 父路由容器 (有 element)
  └─ /b          ← 嵌套子路由
  └─ /c          ← 嵌套子路由
```

> **详细文档**：参见 [vite-plugin-react-auto-router-routing-cases.md](./vite-plugin-react-auto-router-routing-cases.md) 和 [vite-plugin-react-auto-router-nested-enhancement.md](./vite-plugin-react-auto-router-nested-enhancement.md)

## 五、权限设计

### 5.1 权限模型

| 模型 | 说明                                            |
| ---- | ----------------------------------------------- |
| RBAC | 基于角色的访问控制（Role-Based Access Control） |

### 5.2 权限控制总览

前端权限控制分为三个层级，各层级独立运作、协同防护：

| 层级     | 核心职责                   | 数据来源                               | 实现位置                               |
| -------- | -------------------------- | -------------------------------------- | -------------------------------------- |
| 路由权限 | 控制页面是否可访问         | `menus[].access`                       | 路由配置层（filterRoutesByPermission） |
| 菜单权限 | 控制导航菜单是否可见       | `menus[]`（已过滤 `access=0`）         | Layout 侧边栏 / 顶部导航               |
| 按钮权限 | 控制页面内操作按钮的可用性 | `menus[].operations[].operationAccess` | 页面组件内 `usePermission` Hook        |

### 5.3 字段设计

菜单数据结构遵循 **type 与 displayPosition 职责分离** 的设计原则：

- `type` —— 决定**内容类型**（是否有路由、是否加载组件）
- `displayPosition` —— 决定**显示位置**（顶部 / 侧边栏 / 双重显示）
- 两者正交组合，互不影响，各司其职

#### type（内容类型）

| type | 含义             | 有路由 | 加载组件         | 适用场景                      |
| ---- | ---------------- | ------ | ---------------- | ----------------------------- |
| 0    | 目录（仅分组）   | ❌     | ❌               | 顶部 Tab 分组、侧边栏分组标题 |
| 1    | 页面（有路由）   | ✅     | ✅               | 普通业务页面                  |
| 2    | 微应用           | ✅     | ✅（远程）       | qiankun 子应用入口            |
| 3    | iframe（内嵌页） | ✅     | ✅（IframePage） | 内嵌外部系统页面              |

##### type=3 iframe 内嵌页集成

`type=3` 的菜单项通过 `IframePage` 组件在内容区域渲染 iframe，**无需在 `pages` 目录下创建物理页面文件。**

| 维度         | 说明                                                                                                            |
| ------------ | --------------------------------------------------------------------------------------------------------------- |
| 菜单配置     | 必须配置 `path`（路由路径）和 `iframeUrl`（iframe 目标地址）                                                    |
| 路由注册     | `filterRoutesByPermission` 自动为 type=3 菜单注入路由，element 为 `IframePage`，经 `createElementByAccess` 包裹 |
| 地址读取     | `IframePage` 从 `currentRoute.iframeUrl` 读取目标地址（单源，无回退）                                           |
| session 注入 | 路由注入时自动传入 `inject: { session: sessionId }`，透传给 iframe                                              |
| 权限控制     | 与 type=1 一致，`access` 控制页面级可见性和状态                                                                 |

> **设计决策**：type=3 菜单项不需要物理页面文件，路由由 `filterRoutesByPermission` 动态注入。`IframePage` 作为统一渲染组件，通过 `currentRoute.iframeUrl` 区分不同 iframe 内容，避免为每个 iframe 页面创建独立的页面文件。

##### qiankun 微应用集成

项目采用 qiankun 微前端架构，`type=2` 的菜单项作为子应用入口，其路由注册和权限控制遵循以下规则：

| 维度       | 主应用                                                 | 子应用                                 |
| ---------- | ------------------------------------------------------ | -------------------------------------- |
| 菜单配置   | 仅配置子应用顶层入口（`type=2`）                       | 内部菜单由子应用自行管理               |
| 路由注册   | 为子应用入口注册一条父路由，挂载 qiankun 容器组件      | 内部路由由子应用独立注册，主应用不感知 |
| 权限控制   | `access` 控制子应用整体可见性（隐藏/启用/只读/维护中） | 内部页面权限由子应用自行实现           |
| 菜单树透传 | 不解析、不合并子应用内部菜单                           | 可独立调用接口获取自己的菜单树         |

> **设计决策**：主应用对子应用采用**「整体注册、内部自治」**模式。主应用只负责子应用入口的路由注册和页面级权限（`access`），子应用内部的导航结构、路由、按钮权限均由子应用自行管理，主应用不透出或合并子应用内部菜单。

#### displayPosition（显示位置）

| displayPosition | 含义        | 顶部显示 | 侧边栏显示 | 适用场景             |
| --------------- | ----------- | -------- | ---------- | -------------------- |
| 0               | 顶部导航    | ✅       | ❌         | 一级 Tab 分组        |
| 1               | 侧边栏      | ❌       | ✅         | 二级/三级菜单        |
| 2               | 顶部+侧边栏 | ✅       | ✅         | 快捷入口（双重显示） |

#### access（访问权限）

| access | 含义   | 影响范围                                     | 路由注册  | 访问行为                     | 适用场景                     |
| ------ | ------ | -------------------------------------------- | --------- | ---------------------------- | ---------------------------- |
| 0      | 隐藏   | 不生成路由 + 侧边栏不显示                    | ❌ 不注册 | 404（不存在）                | 对当前用户不可见的功能       |
| 1      | 启用   | 生成路由 + 侧边栏正常显示 + 可查看和编辑     | ✅ 注册   | 正常访问                     | 正常可用的功能               |
| 2      | 只读   | 生成路由 + 侧边栏正常显示 + 仅可查看不可编辑 | ✅ 注册   | 可查看，但所有编辑操作被禁用 | 审计期数据锁定、试用期用户等 |
| 3      | 维护中 | 生成路由 + 侧边栏置灰显示                    | ✅ 注册   | 显示"功能维护中"提示页面     | 临时下线、升级中的功能       |

##### 权限层级说明

- `access` 控制**页面级访问权限**：页面能否访问以及以什么模式访问（隐藏 / 启用 / 只读 / 维护中）
- `operations` 数组控制**页面级操作权限**：页面内的具体操作能否使用（按钮、Tab、模块、表单字段等），每个操作对象包含 `name`、`operationCode` 和 `operationAccess`
- 两者**粒度和层级不同**，配合使用实现完整的 RBAC 模型

##### 语义说明

| 字段                             | 语义                                           |
| -------------------------------- | ---------------------------------------------- |
| `access=0`（隐藏）               | 功能对当前用户**不存在**，不注册路由，返回 404 |
| `access=1`（启用）               | 功能**正常可用**，查看 + 编辑均可              |
| `access=2`（只读）               | 功能**仅可查看**，路由存在但编辑操作被禁用     |
| `access=3`（维护中）             | 功能**暂时不可用**，路由存在但显示友好提示页   |
| `operations[].operationAccess=0` | 操作**隐藏**（不渲染）                         |
| `operations[].operationAccess=1` | 操作**展示**（正常显示且可用）                 |
| `operations[].operationAccess=2` | 操作**禁用**（显示但置灰不可点击）             |

##### 操作权限数据结构

```typescript
interface MenuOperation {
  /** 操作名称 */
  name: string;
  /** 操作权限码 */
  operationCode: string;
  /** 操作状态：0=隐藏, 1=展示（可用）, 2=禁用（置灰不可点击） */
  operationAccess: number;
}

> **注意**：菜单类型统一使用 `UrbanSessionMenuResponse`（见 [第九章 接口与数据定义](#5-menus--当前用户可用菜单树)），此处不再单独定义。
```

### 5.4 设计决策

> 完整实现见 [8.1 RoutePermission](#81-routepermission路由权限工具组件) 中的 `FeatureDisabled` 组件。

```typescript

<Menu.Item disabled={menu.access === 3}>
```

#### access=2（只读）推荐实现

> 完整实现见 [8.1 RoutePermission](#81-routepermission路由权限工具组件) 中的 `ReadOnlyWrapper` 和 `ReadOnlyContext`。

```typescript
// 方式 1：路由层自动包裹 ReadOnlyWrapper（推荐，已在 filterRoutesByPermission 中处理）

// 方式 2：通过 operations.operationAccess 控制单个按钮（见 7.2 公共 Hooks）
const { hasPermission, isOperationDisabled } = usePermission();
{hasPermission('person_edit') && <Button>编辑</Button>}
{isOperationDisabled('person_edit') && <Button disabled>编辑</Button>}

// 注意：access=2 已由路由层处理，页面内无需额外判断
```

#### access=0 不注册路由的设计决策

**选择原因：**

1. **安全性更高**：路由不存在，无法通过 URL 直接访问（攻击者无法枚举隐藏页面）
2. **性能更好**：减少路由表大小，提升路由匹配速度
3. **语义更清晰**：隐藏 = 不存在（返回 404），而非无权限（返回 403）
4. **维护成本更低**：不需要在 Guard 层做额外的 access 判断
5. **符合最小权限原则**：不存在的资源无法被访问

**对比方案（运行时拦截）的劣势：**

- ❌ 安全性低：路由存在，知道 URL 就能尝试访问
- ❌ 性能差：路由表包含无效路由
- ❌ 体验差：访问隐藏路由会闪烁（先渲染再跳转 403）
- ❌ 语义混乱：隐藏的路由为什么还能被访问（即使是 403）？

**实现方式：**

```typescript
// 在后端返回菜单后，过滤掉 access=0 的菜单
const validMenus = sessionContext?.menus?.filter((m) => m.access !== 0) || [];

// 使用 filterRoutesByPermission 递归过滤路由树
const protectedRoutes = filterRoutesByPermission(staticRoutes, validMenus);
```

### 5.5 路由权限

**目标**：在路由注册阶段过滤无权限页面，access=0 的菜单不注册路由，命中通配符 `*` 时展示 404 兜底页。

#### 数据流

```mermaid
graph LR
    A["后端 sessionContext"] --> B["menus 树形结构"]
    B --> C["flattenMenuPaths()"]
    C --> D["Set＜全路径 + access＞"]
    E["vite-plugin-react-auto-router"] --> F["静态路由树 routesConfig"]
    F --> G["filterRoutesByPermission()"]
    D --> G
    G --> H["过滤后的路由树"]
    H --> I["React Router 注册"]
```

#### 权限判断流程

```mermaid
graph TD
    A["用户访问 URL"] --> B{"路径在权限 Set 中?"}
    B -->|"否（access=0 或不存在）"| C["路由未注册 → 404 兜底"]
    B -->|"是 access=1"| D["正常渲染页面"]
    B -->|"是 access=2"| E["createElementByAccess → 只读模式渲染"]
    B -->|"是 access=3"| F["createElementByAccess → 维护中提示"]
```

> **路由注册阶段统一处理**：`filterRoutesByPermission()` 在路由注册阶段完成所有 access 状态处理——`access=0` 过滤路由，`access=2/3` 通过 `createElementByAccess()` 包裹对应元素，无需额外的渲染阶段守卫组件。

#### 路由注册规则

- 所有 `access !== 0` 的菜单都注册路由
- `type=0` 注册为父路由容器（`element=null`）
- `type=1/2/3` 注册为页面路由（加载组件）
- `displayPosition` **不影响**路由注册，只影响 UI 渲染位置

#### 核心实现

> `filterRoutesByPermission()` 完整代码见 [8.1 RoutePermission](#81-routepermission路由权限工具组件)。
> App.tsx 路由组装完整代码见 [8.3 App.tsx 路由组装](#83-apptsx-路由组装使用上述公共组件)。

**关键规则**：

- 后端菜单 `path` 必须使用全路径（如 `/urban-management/check-plan`），权限匹配通过 `Set.has()` 实现
- `access=0` 的菜单**不注册路由**，递归过滤路由树
- `access=1/2/3` 的菜单**均注册路由**，`access=2/3` 由 `createElementByAccess()` 在路由注册阶段包裹对应元素
- 父路由自身有 `element`（如 Tabs 页面）且菜单有权限时，即使子路由全部被过滤也**保留父路由**，清空 children；纯嵌套容器（`element=null`）则移除

**示例 1**：父子均有菜单权限

```
后端返回菜单:
[
```

### 5.6 菜单权限

**目标**：根据后端返回的 `menus` 树形数据动态渲染导航菜单，`access=0` 的菜单不显示。

#### 数据流

```mermaid
graph LR
    A["后端 menus 树"] --> B["filterMenusByAccess()"]
    B --> C["过滤后的菜单树"]
    C --> D["按 displayPosition 分组"]
    D --> E["顶部导航 Tab"]
    D --> F["侧边栏菜单"]
```

#### UI 渲染规则

```typescript
// 1. 顶部 Tab：从顶层菜单中过滤 displayPosition=0 的目录
const topTabs = menus.filter((m) => m.displayPosition === 0 && m.access !== 0);

// 2. 当前选中的 Tab
const activeTab = topTabs.find((t) => t.menuId === activeTabId);

// 3. 侧边栏菜单（与当前 Tab 联动）：
//    - 有顶部 Tab 且已选中：从当前 Tab 的 children 中过滤 displayPosition=1/2
//    - 无顶部 Tab 时：直接展示所有 displayPosition=1/2 的顶级菜单（纯侧边栏模式）
//    type=0 的子目录作为分组标题，type=1/2/3 为可点击菜单项
const hasTopTabs = topTabs.length > 0;
const sidebarMenus =
  hasTopTabs && activeTab
    ? activeTab.children?.filter(
        (m) =>
          (m.displayPosition === 1 || m.displayPosition === 2) && m.access !== 0
      ) || []
    : menus.filter(
        (m) =>
          (m.displayPosition === 1 || m.displayPosition === 2) && m.access !== 0
      );
```

#### 组合使用示例

**场景 1：顶部一级 Tab + hover 二级菜单 + 点击展开侧边栏**

```
┌─────────────────────────────────────────────────────────────┐
│  [城市管理]   [序化管理]   [人员管理]   ...          顶部 Tab │  ← displayPosition=0, type=0
```

1. 后端菜单中无 displayPosition=0 的菜单项时，顶部导航栏自动隐藏
2. 侧边栏直接渲染所有 displayPosition=1/2 的菜单（access!=0）
3. type=0 的子目录作为可折叠分组标题，type=1/2/3 为可点击菜单项
4. 侧边栏支持折叠/展开

#### 关键规则

- `type=0`（目录）作为分组标题，不直接导航，其 `children` 展开显示

### 5.7 按钮权限

**目标**：控制页面内操作按钮的显隐和可用性，基于 `operations[].operationAccess` 三值状态。

#### 数据流

```mermaid
graph LR
    A["AdminLayout: useLocation + findMenuByPath"] --> B["setCurrentRoute 写入 Store"]
    B --> C["usePermission 从 Store 读取 operations"]
    C --> D{"operation.operationAccess?"}
    D -->|"0 隐藏"| E["不渲染按钮"]
    D -->|"1 展示"| F["渲染可用按钮"]
    D -->|"2 禁用"| G["渲染置灰按钮"]
```

`operations.operationAccess` 三值语义：

| operationAccess | 含义 | 行为               |
| --------------- | ---- | ------------------ |
| 0               | 隐藏 | 按钮不渲染到 DOM   |
| 1               | 展示 | 正常渲染，可点击   |
| 2               | 禁用 | 渲染但置灰不可点击 |

> `usePermission` Hook 完整实现见 [7.2 公共 Hooks](#72-公共-hooks)。

### 5.8 关键设计约束

1. **后端菜单 `path` 字段必须使用全路径**（以 `/` 开头），如 `/urban-management/check-plan`，避免相对路径拼接带来的匹配错误。
2. **`access=0` 的菜单不注册路由**，通过 `filterRoutesByPermission()` 递归过滤路由树。
3. **`access=2`（只读）和 `access=3`（维护中）**的菜单注册路由，由 `createElementByAccess()` 在路由注册阶段包裹对应元素。
4. **`type` 与 `displayPosition` 职责分离**：
   - `type` 决定内容类型（0=目录，1=页面，2=微应用），控制路由注册和组件加载。
   - `displayPosition` 决定显示位置（0=顶部导航，1=侧边栏，2=两者兼有），控制 UI 渲染位置。
   - `displayPosition` **不影响**路由注册，所有 `access !== 0` 的菜单都注册路由。
5. **权限信息注入**：`filterRoutesByPermission()` 会将 `access`、`type`、`displayPosition`、`operations` 注入到 `route.handle`，按钮权限通过 `usePermission` Hook 从 Store 中的 `currentRoute.operations` 读取。

##### PermissionStore 创建

```typescript
// src/stores/usePermissionStore.ts
import { create } from 'zustand';
import { urbanSessionApi } from '@/services/person';
import type { UrbanSessionContextResponse } from '@/services/person/types';
import useRouteMenuStore from '@/stores/useRouteMenuStore';

const usePermissionStore = create<PermissionState>((set) => ({
  sessionContext: null,
  loaded: false,
  loading: false,
  error: null,

  setSessionContext: (context) => {
    set({ sessionContext: context, loaded: true, error: null });
    useRouteMenuStore.getState().setMenus(context.menus ?? []);
  },

  clearSessionContext: () => {
    set({
      sessionContext: null,
      loaded: false,
      error: null,
    });
    useRouteMenuStore.getState().clearRouteMenu();
  },

  fetchSessionContext: async () => {
    set({ loading: true, error: null });
    try {
      const res = await urbanSessionApi();
      if (res.code === '0' && res.data) {
        set({ sessionContext: res.data, loaded: true });
        useRouteMenuStore.getState().setMenus(res.data.menus ?? []);
      } else {
        // 接口返回非成功状态，标记已加载并记录错误
        set({
          loaded: true,
          error: res?.msg || '获取用户上下文失败',
        });
      }
    } catch (e) {
      // 网络异常等不可恢复错误，标记已加载并展示错误页
      set({
        loaded: true,
        error: e instanceof Error ? e.message : '网络异常，请刷新重试',
      });
    } finally {
      set({ loading: false });
    }
  },
}));
```

##### 菜单数据计算逻辑

菜单 UI 数据处理已内聚在 `useRouteMenuStore` 中，在 `setMenus` / `setActiveTabId` 时自动触发计算：

```typescript
// src/stores/useRouteMenuStore.ts（核心纯计算函数）
/** 将后端菜单树递归转为 UI MenuNode 树（按 sortOrder 升序排序，过滤 access=0） */
const toMenuNodes = (items: UrbanSessionMenuResponse[]): MenuNode[] =>
  [...items]
    .filter((item) => item.access !== 0)
    .sort((a, b) => (a.sortOrder ?? 0) - (b.sortOrder ?? 0))
    .map((item) => ({
      key: item.menuId,
      label: item.menuName,
      path: item.path,
      type: item.type,
      access: item.access,
      icon: item.icon,
      children: item.children?.length ? toMenuNodes(item.children) : undefined,
    }));

/** 计算顶部 Tab：displayPosition=0 且 access!=0 */
const computeTopTabs = (menus) =>
  toMenuNodes(menus.filter((m) => m.displayPosition === 0 && m.access !== 0));

/** 计算侧边栏菜单：根据顶部 Tab 联动 */
const computeSidebarMenus = (menus, topTabs, activeTabId) => {
  const hasTopTabs = topTabs.length > 0;
  if (hasTopTabs && activeTabId) {
    const activeTab = menus.find((m) => m.menuId === activeTabId);
    if (activeTab) {
      return toMenuNodes(
        activeTab.children.filter(
          (m) =>
            (m.displayPosition === 1 || m.displayPosition === 2) &&
            m.access !== 0
        )
      );
    }
    return [];
  }
  if (!hasTopTabs) {
    return toMenuNodes(
      menus.filter(
        (m) =>
          (m.displayPosition === 1 || m.displayPosition === 2) && m.access !== 0
      )
    );
  }
  return [];
};

// setMenus 时自动计算 topTabs / sidebarMenus
setMenus: (menus) => {
  const topTabs = computeTopTabs(menus);
  const sidebarMenus = computeSidebarMenus(menus, topTabs, null);
  set({ menus, topTabs, sidebarMenus });
};

// setActiveTabId 时自动重算侧边栏
setActiveTabId: (activeTabId) => {
  const { menus, topTabs } = get();
  const sidebarMenus = computeSidebarMenus(menus, topTabs, activeTabId);
  set({ activeTabId, sidebarMenus });
};
```

#### usePermission 实现

```typescript
// src/hooks/usePermission.ts
import { useCallback } from 'react';
import useRouteMenuStore from '@/stores/useRouteMenuStore';

interface UsePermissionReturn {
  /** 检查操作是否可见（operationAccess≠0 即渲染，operationAccess=2 时配合 isOperationDisabled 禁用） */
  hasPermission: (operationCode: string) => boolean;
  /** 检查操作是否禁用（operationAccess=2） */
  isOperationDisabled: (operationCode: string) => boolean;
  /** 获取操作完整信息 */
  getOperation: (operationCode: string) => MenuOperation | undefined;
}

export const usePermission = (): UsePermissionReturn => {
  const currentRoute = useRouteMenuStore((state) => state.currentRoute);

  const hasPermission = useCallback(
    (operationCode: string) => {
      const op = currentRoute?.operations?.find(
        (item) => item.operationCode === operationCode
      );
      // operationAccess≠0 即渲染，operationAccess=2 时配合 isOperationDisabled 置灰
      return op !== undefined && op.operationAccess !== 0;
    },
    [currentRoute?.operations]
  );

  /** 检查操作是否禁用 */
  const isOperationDisabled = useCallback(
    (operationCode: string) => {
      const op = currentRoute?.operations?.find(
        (item) => item.operationCode === operationCode
      );
      return op?.operationAccess === 2;
    },
    [currentRoute?.operations]
  );

  const getOperation = useCallback(
    (operationCode: string) => {
      return currentRoute?.operations?.find(
        (op) => op.operationCode === operationCode
      );
    },
    [currentRoute?.operations]
  );

  return {
    hasPermission,
    isOperationDisabled,
    getOperation,
  };
};
```

#### findMenuByPath 实现

```typescript
// src/utils/routeMenuPermission/findMenuByPath.ts
import type { UrbanSessionMenuResponse } from '@/services/person/types';

/**
 * 从菜单树中按路径递归查找菜单项
 * 匹配前统一去除尾部斜杠，避免因路径格式差异导致匹配失败
 */
export function findMenuByPath(
  items: UrbanSessionMenuResponse[],
  path: string
): UrbanSessionMenuResponse | undefined {
  // 统一规范化：去除尾部斜杠，保证根路径为 '/'
  const target = path.replace(/\/+$/, '') || '/';

  function traverse(
    tree: UrbanSessionMenuResponse[]
  ): UrbanSessionMenuResponse | undefined {
    for (const node of tree) {
      const nodePath = node.path.replace(/\/+$/, '') || '/';
      if (nodePath === target) return node;
      if (node.children?.length) {
        const found = traverse(node.children);
        if (found) return found;
      }
    }
    return undefined;
  }

  return traverse(items);
}
```

#### filterRoutesByPermission 实现

```typescript
// src/utils/routeMenuPermission/filterRoutesByPermission.ts
import { createElementByAccess } from '@/components/RoutePermission';
import type { UrbanSessionMenuResponse } from '@/services/person/types';
import type { RouteObject } from 'react-router-dom';

/**
 * 基于后端菜单配置过滤路由树
 * @param staticRoutes 插件生成的静态路由（routes.tsx）
 * @param menus 后端返回的菜单树（全路径）
 * @returns 过滤后的动态路由配置
 */
export function filterRoutesByPermission(
  staticRoutes: RouteObject[],
  menus: UrbanSessionMenuResponse[]
): RouteObject[] {
  /** 收集所有 access!=0 的菜单路径及其配置 */
  const validMenuPaths = new Set<string>();
  const menuAccessMap = new Map<string, UrbanSessionMenuResponse>();

  const collectMenuPaths = (items: UrbanSessionMenuResponse[]) => {
    items.forEach((menu) => {
      if (menu.access !== 0) {
        validMenuPaths.add(menu.path);
        menuAccessMap.set(menu.path, menu);
      }
      if (menu.children) {
        collectMenuPaths(menu.children);
      }
    });
  };
  collectMenuPaths(menus);

  /**
   * 递归过滤路由树
   * 注意：parentPath 始终传入父路由的原始路径（而非累加路径），
   * 因为自动路由插件生成的是绝对路径，子路由的 path 是相对路径
   */
  const filterRouteTree = (
    routes: RouteObject[],
    parentPath = ''
  ): RouteObject[] => {
    return routes
      .map((route) => {
        const routePath = route.path || '';

        // 子路由是相对路径，需拼接父路由的原始路径得到全路径
        const fullPath = routePath.startsWith('/')
          ? routePath
          : parentPath
            ? `${parentPath}/${routePath}`.replace(/\/+/g, '/')
            : `/${routePath}`;

        const hasAccess = validMenuPaths.has(fullPath);
        const menuConfig = menuAccessMap.get(fullPath);

        // 递归处理子路由，传入父路由的原始路径（非 fullPath）
        const filteredChildren = route.children
          ? filterRouteTree(route.children, routePath || parentPath)
          : [];

        // 有子路由但过滤后为空
        if (route.children?.length && filteredChildren.length === 0) {
          // 父路由自身有 element（如 Tabs 页面）且菜单有权限：保留父路由，清空子路由
          if (route.element && hasAccess) {
            const element = createElementByAccess(
              route.element,
              menuConfig?.access ?? 1
            );
            return {
              ...route,
              element,
              children: [],
              handle: {
                access: menuConfig?.access,
                type: menuConfig?.type,
                displayPosition: menuConfig?.displayPosition,
                operations: menuConfig?.operations,
                menuName: menuConfig?.menuName,
              },
            };
          }
          // 纯嵌套容器（element=null）或无权限：移除
          return null;
        }

        // 叶子路由且不在菜单中：无权限，移除
        if (!route.children?.length && !hasAccess) {
          return null;
        }

        // 有子路由的父容器（element=null 或 layout 组件）：保持原样
        // 叶子路由：根据 access 创建对应元素
        const isParentRoute = route.children && route.children.length > 0;
        const element = isParentRoute
          ? route.element
          : createElementByAccess(route.element, menuConfig?.access ?? 1);

        return {
          ...route,
          element,
          // children 设为 undefined 而非空数组，让 react-router 将其视为叶子路由
          children: filteredChildren.length > 0 ? filteredChildren : undefined,
          handle: {
            access: menuConfig?.access,
            type: menuConfig?.type,
            displayPosition: menuConfig?.displayPosition,
            operations: menuConfig?.operations,
            menuName: menuConfig?.menuName,
          },
        };
      })
      .filter(Boolean) as RouteObject[];
  };

  const filteredRoutes = filterRouteTree(staticRoutes);

  /**
   * 为 type=3（iframe 内嵌页）的菜单项注入路由
   * IframePage 同样经过 createElementByAccess 包裹，保证 access=2/3 语义一致
   */
  const injectIframeRoutes = (
    items: UrbanSessionMenuResponse[],
    result: RouteObject[]
  ) => {
    const sessionId = usePermissionStore.getState().sessionContext?.sessionId;
    items.forEach((menu) => {
      if (menu.type === 3 && menu.access !== 0) {
        const exists = result.some((r) => {
          const rp = r.path?.startsWith('/') ? r.path : `/${r.path}`;
          return rp === menu.path;
        });
        if (!exists) {
          const iframeElement = React.createElement(IframePage, {
            inject: { session: sessionId },
          });
          result.push({
            path: menu.path.startsWith('/') ? menu.path.slice(1) : menu.path,
            // iframe 路由也走 access 包裹，保持只读/维护中语义一致
            element: createElementByAccess(iframeElement, menu.access),
            handle: {
              access: menu.access,
              type: menu.type,
              displayPosition: menu.displayPosition,
              operations: menu.operations,
              menuName: menu.menuName,
            },
          });
        }
      }
      if (menu.children?.length) {
        injectIframeRoutes(menu.children, result);
      }
    });
  };

  injectIframeRoutes(menus, filteredRoutes);

  return filteredRoutes;
}
```

#### createElementByAccess

根据 access 状态创建对应路由元素（维护中/只读/正常）的工厂函数。

**触发条件**：`filterRoutesByPermission` 递归过滤路由树时，对每个菜单节点调用。

```typescript
// src/components/RoutePermission/createElementByAccess.tsx
import React from 'react';
import { FeatureDisabled } from './featureDisabled';
import { ReadOnlyWrapper } from './readOnlyWrapper';

/**
 * 根据 access 状态创建对应的路由元素
 * - access=0：返回 null（不注册路由）
 * - access=3：返回 FeatureDisabled 组件（功能维护中）
 * - access=2：用 ReadOnlyWrapper 包裹（只读模式）
 * - access=1 或其他：正常返回
 */
export function createElementByAccess(
  element: React.ReactNode,
  access: number
): React.ReactNode {
  if (access === 0) {
    return null;
  }
  if (access === 3) {
    return <FeatureDisabled />;
  }
  if (access === 2) {
    return <ReadOnlyWrapper>{element}</ReadOnlyWrapper>;
  }
  return element;
}
```

### 8.2 IframePage（iframe 内嵌页面组件）

> 文件路径：`src/components/IframePage/`

**职责**：通用 iframe 嵌入页面组件，从 `useRouteMenuStore.currentRoute.iframeUrl` 读取地址进行嵌入渲染。

**使用场景**：由 `filterRoutesByPermission` 自动为 type=3 的菜单项注入路由，element 为 IframePage，经 `createElementByAccess` 包裹。

```typescript
// src/components/IframePage/types.ts
export interface IframePageProps {
  /** 注入到 iframe URL 的查询参数 */
  inject?: Record<string, string | number | undefined | null>;
}
```

```tsx
// src/components/IframePage/index.tsx
import useRouteMenuStore from '@/stores/useRouteMenuStore';
import { Spin } from 'antd';
import React, { useMemo, useState } from 'react';
import type { IframePageProps } from './types';

/**
 * 通用 iframe 嵌入页面
 * 从 useRouteMenuStore.currentRoute.iframeUrl 获取 iframe 地址
 */
const IframePage: React.FC<IframePageProps> = ({ inject }) => {
  const currentRoute = useRouteMenuStore((state) => state.currentRoute);
  const [loading, setLoading] = useState(true);

  /** 将 inject 对象转为 URL 查询参数 */
  const iframeUrl = useMemo(() => {
    const baseUrl = currentRoute?.iframeUrl || '';
    if (!baseUrl) return '';
    if (!inject) return baseUrl;
    const url = new URL(baseUrl);
    Object.entries(inject).forEach(([key, value]) => {
      url.searchParams.set(key, String(value));
    });
    return url.toString();
  }, [currentRoute, inject]);

  useEffect(() => {
    setLoading(true);
  }, [iframeUrl]);

  if (!iframeUrl) {
    return (
      <div className="flex items-center justify-center h-full text-gray-400">
        暂无外部页面地址配置
      </div>
    );
  }

  return (
    <div className="h-full">
      <Spin spinning={loading} tip="加载中...">
        <iframe
          title={currentRoute?.menuName || '内嵌页面'}
          src={iframeUrl}
          className="w-full h-full border-0"
          allowFullScreen
          onLoad={() => setLoading(false)}
        />
      </Spin>
    </div>
  );
};

export default IframePage;
```

```typescript
// 获取菜单列表
const menus = usePermissionStore((state) => state.sessionContext?.menus || []);
```

## 十一、开发规范

### 目录规范

| 目录          | 用途                           | 规范                                                                |
| ------------- | ------------------------------ | ------------------------------------------------------------------- |
| `pages/`      | 页面级组件，自动生成路由       | 每个页面独立文件夹，私有组件放 `components/`，私有 hook 放 `hooks/` |
| `components/` | 多页面复用的公共组件           | 大驼峰命名，主文件 `index.tsx`，样式 `index.module.less`            |
| `stores/`     | 全局 Zustand Store             | 仅放公共状态，页面私有的放页面目录                                  |
| `services/`   | API 请求封装（按模块分文件夹） | 每个模块独立文件夹，统一错误处理                                    |

### 路由生成约定

1. **`_layout.tsx` 必须渲染 `<Outlet />`**，否则子页面不会显示
2. **无 `_layout.tsx` 时子目录平铺**（nestedByDirectory: false），不需要 `Outlet`
3. **layout-only 目录访问父路径会显示空内容**，如需默认页请补充 `index.tsx`
4. `components/`、`hooks/`、`Layout/` 目录会被插件排除，不生成路由
5. **`guard.tsx` 为可选功能**，当前项目暂不需要，后续有特殊权限校验需求时再引入
6. **`access=0` 的菜单不注册路由**，使用 `filterRoutesByPermission()` 递归过滤路由树
7. **`access=2`（只读）和 `access=3`（维护中）**的菜单注册路由，由 `createElementByAccess()` 在路由注册阶段包裹对应元素
8. **后端菜单 `path` 字段必须使用全路径**（以 `/` 开头），如 `/urban-management/check-plan`
9. **`type` 与 `displayPosition` 职责分离**：
   - `type` 决定内容类型（0=目录，1=页面，2=微应用），控制路由注册和组件加载
   - `displayPosition` 决定显示位置（0=顶部导航，1=侧边栏，2=两者兼有），控制 UI 渲染位置
   - `displayPosition` **不影响**路由注册，所有 `access !== 0` 的菜单都注册路由
10. **nestedByDirectory: true 时**，父路由容器没有 `index.tsx` 则 `element` 为 `null`，访问父路径显示空白
11. **向后兼容**: 默认 `nestedByDirectory: false`，保持现有 `_layout.tsx` 作为嵌套开关的行为
12. **路由结构变化**: 启用 `nestedByDirectory: true` 后，所有有子目录的页面都会变成嵌套路由，需确认菜单配置和权限控制是否适配
13. **权限信息注入**: `filterRoutesByPermission()` 会将 `access`、`type`、`displayPosition`、`operations` 注入到 `route.handle`，按钮权限通过 `usePermission` Hook 从 Store 读取
